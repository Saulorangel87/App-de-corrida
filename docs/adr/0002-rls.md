# ADR 0002 — Row-Level Security e papéis do banco

Data: 2026-10-10 · Status: aceito

## Contexto
A seção 10.2 pede que todo acesso a dados do atleta seja filtrado pelo dono da sessão e que se avalie RLS como camada extra. A 10.3 pede um usuário da API sem superusuário e outro só para migrações.

## Decisão
- **Papéis:** `passo_migrator` é dono do schema e roda migrações e seed; `passo_api` só tem `SELECT/INSERT/UPDATE/DELETE` (catálogo só leitura; `engine_decisions` só `SELECT/INSERT`). Nenhum é superusuário ou tem `BYPASSRLS`. Criados por `ops/db-roles.sh`; permissões na migração `0001_rls.sql`.
- **RLS ligado nas 9 tabelas do atleta** (`consents`, `athlete_profiles`, `interview_responses`, `athlete_plans`, `scheduled_workouts`, `workout_logs`, `daily_checkins`, `pain_reports`, `engine_decisions`), com `USING` e `WITH CHECK` em `user_id = app.user_id`.
- `app.user_id` é definido só por `withAthlete(db, userId, fn)` (`packages/db`), com `set_config(..., true)`: vale só na transação. Sem ele, nenhuma linha passa. O `userId` vem sempre da sessão no servidor.
- **Sem RLS em `users`, `sessions` e `auth_tokens`:** o login e a validação de sessão acontecem antes de existir um dono conhecido. Essas tabelas só são acessadas por `apps/api/src/repositories/auth-repository.ts`, que filtra pelo dono em toda operação de sessão.
- RLS é a segunda camada: as rotas continuam filtrando por `user_id` e devolvendo 404 para recurso de outro usuário, com teste A-tenta-B.

## Alternativas
- RLS também em `users`/`sessions` com funções `SECURITY DEFINER` para o login: mais peças para pouco ganho.
- Sem RLS (só filtro na aplicação): descartado; um esquecimento numa consulta vazaria dados de saúde.

## Consequências
- Toda consulta a dados do atleta precisa rodar dentro de `withAthlete` (uma transação por chamada).
- Testes em `apps/api/test/rls.test.ts` rodam com o papel restrito, como em produção.
